# Білінг — частини, правила списання, маршрути

Модуль веде **журнал юнітів** (рахунки, партії, рухи, резерви) і ставить його на шлях кожної платної
дії: перевірки роботи студента, обробки матеріалу автора, підготовки завдання. Задачі BIL-A…BIL-E,
BIL-E2, BIL-TESTMARK; рішення оператора — у docstring кожного модуля.

## Частини

| Модуль | Що робить |
|---|---|
| `accounts.py` | Рахунки: створення першою дією, що змінює стан (запис `account.create`), знеособлення |
| `payer.py` | **Єдине** місце, що вирішує, хто платить: правило для студента → правило курсу → «сам»; `resolve_payer` для дії, `find_payer` для читання |
| `ledger.py`, `journal.py` | Журнал: купівля, резерв, списання факту, звільнення, різниця |
| `charging.py` | Ціна P, поріг, резерв, факт — усе в юнітах; перемикачі `BILLING_CHARGING_ENABLED` і `BILLING_CHARGING_MARKED` |
| `funds.py` | Порт коштів журналу (`LedgerFundsPort`) і ворота обробки та підготовки |
| `estimates.py` | E (очікувана вартість) у пам'яті; збій оцінки перевірки — `None`: діє стеля |
| `quotes.py` | Ціна перед дією для екранів і воріт подачі (`review_quote`, `review_price`, `author_quote`) |
| `held.py` | Утримані перевірки: хто платить, скільки бракує, які чекають автора |
| `resume_funded.py` | Продовжує утримані перевірки, щойно платник може заплатити |
| `outlook.py` | Нагадування: на скільки перевірок / днів вистачить юнітів |
| `public_numbers.py` | Публічні числа: вартість перевірки й «на скільки вистачить» пакета — один знімок на старт app |
| `links.py` | Зв'язок «рух журналу → курс → завдання» — один для `spending.py` і `costs.py` |
| `spending.py` | Витрати автора в юнітах по курсах і завданнях (без доларів) |
| `costs.py` | Звіт адміністратора: собівартість у доларах поруч із виставленими юнітами |
| `testmark.py` | Позначка тестових купівель і зняття їхніх вільних юнітів (BIL-TESTMARK) |

## Правила списання (`charging.py`)

* **Ціна** `P = ceil(E × (1 + margin) × K)`; **стеля** `N = ceil(стеля шляху USD × K)` — без запасу,
  та сама величина, що обмежує резерв (`ceiling_units`).
* **Поріг** `available ≥ P` (`threshold_applies`): студент за власну перевірку; автор без кредиту — за
  власну дію **і за перевірку студента за правилом оплати** (BIL-E2, 5а п. 2: платформа в борг не
  працює). Автор із `credit_allowed` — без порогу. Підготовка, яку запустила подача студента, —
  без порогу.
* **Тест** (вид `test`) безкоштовний, поки баланс платника (разом із зарезервованим) > 0 — для
  студента і для автора за правилом; автор із кредитом — завжди.
* **Резерв** на старті — `min(2E, стеля, доступне)`; **факт** — вартість викликів реєстру, які оплачує
  платник (`charging.PAID_BY_PAYER`, рішення оператора 17.11): `request_kind` `first`, `item_repeat`
  і рядки без виду (`NULL`: STT, старі рядки); `structural_retry`, `infra_retry` і будь-яку спробу,
  що сама впала на інфраструктурі (`outcome = 'transport_error'`, зокрема `NULL`), несе платформа. Окремо, незалежно
  від виду, — виклики екрана реплік (`charging.REPLY_SCREEN_CALL`, `action = 'reply_safety'`): у факт
  перевірки не входять. За тим самим визначенням — калібрування (`scripts/cost_estimate_report.py`).
  Платник без
  кредиту платить не більше резерву, перевитрату бере платформа (`platform_covered`) — це не борг.
  Розпочата дія доходить до кінця.
* **Оцінка впала на стелю** (BIL-E2, 4а): будь-який збій — вибір шляху, читання файла (крім відмови
  дверей), типовий розмір, сама оцінка, не задано K — на екрані ціна N («не більше N»). Поріг
  (рішення оператора 15.11) — **типова ціна завдання** (як для `basis: "typical"`: медіана розміру з
  історії завдання або `typical_submission.chars`, із запасом margin); не вдалося й її — `available > 0`.
  Резерв — `min(N, доступне)`, списується факт, перевитрату понад резерв бере платформа. Одна функція
  `quotes.ceiling_threshold` — для воріт подачі, порту коштів на старті прогону й продовження
  утриманих; автор за правилом — те саме правило з його юнітами.
  Журнал — по одному попередженню `billing_quote_ceiling` на кожну невдалу оцінку, з `reason`
  (`path_choice_failed` | `file_read_failed` | `typical_size_failed` | `estimate_failed` |
  `rate_not_set`) і класом помилки, без тексту роботи. Без K усе коштує 0, і N теж 0.

Поки обидва перемикачі вимкнені, `build_funds_port` дає `AlwaysEnoughFundsPort`: нічого не
резервується й не утримується.

## Кого списують: два перемикачі (рішення оператора 17.11, «1б»)

* `BILLING_CHARGING_ENABLED` — списання для всіх платників. Увімкнений — другий перемикач нічого не
  змінює.
* `BILLING_CHARGING_MARKED` — списання лише для платника, чий рахунок має позначку адміністратора
  `test_purchase_allowed` (`scripts/billing_admin.py test-purchase`). У курсі, де платить автор
  (правило оплати), вирішує позначка рахунку автора, а не студента. Решта платників — рівно як при
  вимкненому списанні: резерву, відмови й утримання немає, рахунок не створюється, у журнал і в
  `billing_audit_log` нічого не пишеться.

Два питання в `charging.py`: `charging_possible()` — «списання можливе» (є хоч один із перемикачів),
для місць, де платника ще немає: вибір порту, продовження утриманих, кінець обробки (розраховує лише
те, що зарезервував старт), двері подачі (рішення приймає оцінка за платником).
`charging_applies(session, account_id)` — «списання застосовне до цього платника», для решти місць
після того, як платника визначено. Старт платної дії (`charged_payer_of`) спершу **читає** платника
(`find_payer_of`) і лише коли списання застосовне, іде сьогоднішнім шляхом `payer_of`.
`charging_enabled()` читають лише ці дві функції.

**Позначка `test_purchase_allowed` має два значення:** (а) рахунок може купувати, поки посередник у
тестовому режимі або увімкнений `BILLING_PURCHASE_MARKED_ONLY`; (б) з рахунку списують, поки
`BILLING_CHARGING_ENABLED` вимкнений, а `BILLING_CHARGING_MARKED` увімкнений. Знімається для обох
значень разом — коли купівлю відкривають усім і загальне списання й так вмикається.

## Коли з'являється рахунок (`accounts.py`, BIL-E3)

Рахунок створює **перша дія, що змінює стан**: згода, оформлення купівлі, позначка, налаштування,
правило чи нарахування адміністратора, старт платної дії (`resolve_payer` / `charging.payer_of`).
У тій самій транзакції пишеться один запис `billing_audit_log`: `action = "account.create"`,
`entity = "account"`, `before = null`, `after = audit.account_snapshot` (без власника); `actor` —
`--actor` адміністратора, для дії користувача чи системи — `audit.SYSTEM_ACTOR = "system"`. Запис
пише лише виклик, чия вставка повернула рядок (`RETURNING`): дві одночасні перші дії дають один
рахунок і один запис.

**Читання рахунку не створює:** GET маршрути білінгу, маршрути оцінки, нагадування, списки порталу
з утриманими перевірками й команда `get-settings` читають через `accounts.find_active_account` і
`payer.find_payer` / `charging.find_payer_of`. Без рахунку відповідь — як для порожнього: усі складники
залишку 0, виписка порожня, `expiring_soon = null`, `consent_required = true`, нагадування — за
правилами порожнього рахунку, `purchase` — як для непозначеного.

## Утримана перевірка (`held.py`, `resume_funded.py`)

Відмова порту на старті прогону — стан `awaiting_funds` (файл, контрольна точка й місце
зберігаються). Чиїх юнітів він чекає, каже `charging.payer_of` — одне джерело правди для прогону,
продовження, порталу й панелі автора:

* студент платить сам — код порталу `awaiting_funds`;
* автор за правилом — код порталу `awaiting_author_funds`, і лічильник `held_reviews` у
  `GET /billing/outlook` автора.

`resume_funded` продовжує найстаріші першими: автор із кредитом — одразу; платник, до якого списання
більше не застосовне (позначку зняли, поки перевірка чекала), — одразу, і прогін нічого не резервує
й не списує; інакше доступне ≥ P з рядка оцінки, а без рядка — поріг стелі `ceiling_threshold`
(типова ціна, інакше доступне > 0); тест — баланс > 0.

## Тестові купівлі (`testmark.py`, BIL-TESTMARK)

Поки посередник у тестовому режимі, тестова картка платить, а зараховується справжня партія
юнітів. Рішення оператора 16.11: такі партії позначені в базі й знімаються однією командою
адміністратора — перед увімкненням списання (`BILLING_CHARGING_ENABLED`).

* **Позначка** — таблиця `billing_test_batches` (`batch_id`, `marked_at`, `marked_by`), лише
  дописування (тригер `billing_refuse_update`; DELETE — лише п'ятирічне знищення, разом із партією).
  `marked_by = credit`: купівлю зараховано як тестову — посередник, що перевірив підпис події, був у
  тестовому режимі (`PaymentProvider.test_mode`) або увімкнений `BILLING_PURCHASE_MARKED_ONLY`
  (`payments/checkout.is_test_purchase`); позначка в тій самій транзакції, що й партія
  (`payments/webhooks.py`). У бойовому режимі без налаштування позначки немає. `marked_by = backfill`: міграція
  `biltestmark_test_batches` позначила всі купівлі Creem, зроблені до неї (бойових ключів Creem на
  проді не було). Рахунок-фактура B2B і нарахування адміністратора не позначаються.
* **Зняття** — вільні юніти (`journal.available`) кожної позначеної партії виходять одним рухом
  `test_voided` (входить в `OUTFLOW_KINDS`: баланс зменшується). Зарезервовані й утримані
  (повернення, спір) юніти лишаються — команда їх друкує; наступний запуск забере те, що звільнилось.
  Повтор без вільних юнітів нічого не змінює. Аудит — `batch.test_void` на партію, з якої щось
  знято: `before` / `after` = `{"free_units": n}` (до й після, після — 0).
* **Виписка** — рядок `test_voided`: `affects_balance = true`, юніти зі знаком мінус.

```bash
uv run python scripts/billing_admin.py void-test-batches --actor <ім'я> [--account <id>] [--dry-run]
uv run python scripts/billing_admin.py show-account --account <id>   # рядок «test units=N»
```

`--dry-run` — транзакція READ ONLY: той самий вивід, нічого не записано. Вивід — рахунок (id і
вид, без ідентифікаторів власника), партія, `voided`, `left reserved`, `left held`; у кінці підсумок.

## Тестовий студент (`students.is_test_student`, Б-5, DD-BIL-CAL)

Наші службові студенти — контрольні, репетиційні, студенти перевіряльника посередника оплати.
Їхні роботи перевіряються по-справжньому, але спотворюють калібрування оцінки вартості перевірки
(контрольні архіви набагато більші за типову роботу). Позначка — поле студента (не рахунку білінгу),
типово `false`; міграція `biltest_student_flag` нічого не заповнила.

* **Хто ставить** — адміністратор: `billing_admin.py test-student --student <id> --mark | --unmark
  --actor <ім'я>` (друкує «було → стало»; повтор нічого не змінює; невідомий чи видалений студент —
  відмова) і `test-student --list` (лише читання: id студента й орендаря, кількість). Зміна — рядок
  журналу `student_test_mark_set` з `actor`, `student_id`, `before`, `after`, **не** запис
  `billing_audit_log`: п'ятирічне знищення журналу аудиту (`retention.py`) іде за рахунками, а
  позначка не на рахунку — запис про студента лишився б назавжди.
* **Хто читає** — лише звіт калібрування (`scripts/cost_estimate_report.py`,
  `cost_estimate.report.select_reviews`): перевірки тестових студентів за замовчуванням не входять,
  `--include-test-students` повертає їх; рядок звіту — скільки виключено і скільки різних нетестових
  студентів у вибірці review. Оцінки обробки й підготовки фільтр не чіпає.
* **Свідомо не читають** — шлях перевірки (homework/, agents/, llm/, workers/; замок —
  `tests/unit/test_test_student_not_read.py`), публічні числа (`public_numbers.py`: поки рахуються
  разом зі службовими, `includes_internal = true`), нагадування, ворота подачі, резерв, списання.
  Назовні (схеми API) поле не віддається.

```bash
uv run python scripts/billing_admin.py test-student --student <id> --mark --actor <ім'я>
uv run python scripts/billing_admin.py test-student --list
uv run python scripts/cost_estimate_report.py [--include-test-students]
```

## Бойовий режим до схвалення магазину (BIL-LIVE, рішення оператора 18.11)

Creem перевіряє магазин лише в бойовому режимі: перевіряльник купує одноразовим кодом знижки 100 %
(замовлення нульової суми). До схвалення будь-яка купівля — тест або демо перевіряльника.

* **`BILLING_PURCHASE_MARKED_ONLY`** (типово `false`). Увімкнений — купують лише рахунки з позначкою
  `test_purchase_allowed` за будь-якого режиму посередника (`purchase_closed`: пакети —
  `purchase.open = false`, `reason = purchase_not_open`; оформлення — 403), і кожна зарахована
  купівля позначається як тестова (`marked_by = credit`, та сама транзакція) — її юніти знімає
  `void-test-batches` перед загальним списанням. Правило одне: `checkout.is_test_purchase` — «посередник
  у тестовому режимі АБО налаштування». Знімається, коли купівлю відкривають усім.
* Налаштування читає лише API: `build_registry` кладе його в `ProviderRegistry.purchase_marked_only`
  (раз на процес); маршрути пакетів, оформлення й вебхука беруть його з реєстру. Тести підставляють
  `ProviderRegistry([...], purchase_marked_only=True)` — без латок налаштувань.
* **Бойові ідентифікатори товарів** — `providers_live.creem` у `config/billing_packages.yaml`
  (вписані: товари бойового кабінету Creem, створені 18.11, для чотирьох активних пакетів).
  Оформлення в бойовому режимі (`CREEM_API_BASE=https://api.creem.io/v1`, `test_mode = False`) бере
  ідентифікатор лише звідти, у тестовому — з `providers.creem`. Пакет без бойового ідентифікатора в
  бойовому режимі не купується: 503 `payment_unavailable`, тестовий ідентифікатор туди не йде.
  Вебхук визначає пакет за `metadata.package_id` оформлення, не за ідентифікатором товару.
* **Нульова сума**: `order.amount_paid = 0` зараховує юніти пакета з `amount_paid_minor = 0`. Без поля
  `amount_paid` (або `null`) подія відхиляється (400, лог `billing_webhook_refused`), нуль не вигадується.

**Порядок перемикання проду** (кожна зміна `.env.prod` — перестворення app:
`docker compose --env-file .env.prod -f docker-compose.prod.yaml up -d app`; воркери налаштувань
купівлі не читають):

1. **Викласти цей запит** (разом із бойовими ідентифікаторами в `providers_live.creem`).
   Перевірити: app здоровий; посередник ще тестовий — поведінка як раніше (непозначений рахунок:
   `GET .../billing/packages` → `purchase_not_open`).
2. **`BILLING_PURCHASE_MARKED_ONLY=true`**, перестворити app. Перевірити:
   `docker compose ... exec app python -c "from course_supporter.config import get_settings;
   print(get_settings().billing_purchase_marked_only)"` → `True`; пакети для непозначеного —
   `purchase_not_open`, для позначеного — `open = true`.
3. **Бойові `CREEM_API_BASE=https://api.creem.io/v1`, `CREEM_API_KEY`, `CREEM_WEBHOOK_SECRET`**
   (з кабінету Creem поза Test Mode; адреса вебхука в бойовому кабінеті —
   `https://<api host>/api/v1/billing/webhooks/creem`), перестворити app. Бойові ідентифікатори
   товарів викладені на кроці 1 (без них оформлення — 503). Перевірити:
   непозначений — пакети `purchase_not_open`, оформлення 403; позначений — оформлення повертає
   посилання Creem бойового режиму; у логах app немає `billing_creem_product_unknown`.
4. **Перша бойова купівля позначеним рахунком.** Перевірити: рядок `billing_provider_events`
   `processed`; партія з юнітами пакета й сумою з події (0 для коду 100 %); позначка
   `billing_test_batches.marked_by = credit` (`show-account` → `test units=N`); стан оформлення
   `credited`; у логах app — `billing_test_purchase_marked`. Подія `ignored` (статус замовлення не
   `paid`) або 400 без `amount_paid` — зупинитися й розібратися: ці поля для нульового замовлення ще
   не перевірені на бойовому Creem.

## Маршрути

| Маршрут | Хто | Що |
|---|---|---|
| `POST /portal/tasks/{id}/estimate` | студент | ціна перевірки: `price_units`, `available_units`, `enough`, `missing_units`, `charging_enabled`, `basis`, `paid_by` |
| `POST /nodes/{id}/documents/estimate` | автор (`prep`) | ціна обробки матеріалу: `price_units`, `available_units`, `enough`, `missing_units`, `charging_enabled`, `unpriced_reason`, `missing_features` |
| `POST /documents/{id}/reference/estimate` | автор (`prep`) | ціна пояснень ключа тесту (ті самі поля) |
| `GET /portal/billing/outlook` | студент | `reviews_left`, `warning`, `expiring_soon`, `paid_by`, `charging_enabled` |
| `GET /billing/outlook` | автор (`prep`) | `days_left`, `warning`, `expiring_soon`, `held_reviews`, `charging_enabled` |
| `GET /billing/spending?from=&to=` | автор (`prep`) | витрати в юнітах по курсах і завданнях |
| `GET /public/numbers` | будь-хто, без входу й ключа | публічні числа (нижче) |

**Оцінка перевірки студента.** `basis`: `typical` (типовий розмір роботи), `file` (надісланий файл),
`ceiling` (оцінку не вдалося отримати: `price_units` = N — «не більше N», спишеться факт). Перевірку
оплачує автор (`paid_by = "author"`): `price_units`, `available_units`, `missing_units` = `null`,
`enough = true` — подачу приймаємо завжди, чи почнеться перевірка, вирішує прогін. Відмова дверей —
422 `{"detail": {"code", "details"}}`, як і подача.

**Оцінка дії автора без ціни** (BIL-E3). Коли E порахувати не можна, `price_units` і `missing_units` —
`null`, `enough = true` (заздалегідь не відхиляємо: поріг за справжніми ознаками перевіряє старт
роботи), а `unpriced_reason` каже чому: `missing_features` — у тілі бракує ознаки, потрібної виду
матеріалу (`missing_features` — назви полів тіла: audio/video — `duration_sec`; presentation —
`slides`, `text_chars`; text/web — `text_chars`; code — `files`, `text_chars`; таблиця —
`cost_estimate.actions.REQUIRED_FACTORS`), або `estimate_failed` — збій самої оцінки. З ціною обидва
поля `null`.

**`charging_enabled`** у нагадуваннях, оцінках і витратах — «списання застосовне до рахунку, про
який ця відповідь» (`charging.charging_applies`): для автора — його рахунок; для оцінки — платник
дії; для нагадування студента — платник його перевірок, якого називає `paid_by` (з `?course_id=` —
за правилом цього курсу, без нього — правило для студента або сам студент). Решта полів від нього не
залежить — що показувати, поки списання не застосовне, вирішує екран. (Оцінка перевірки студента
додає ще тестовий режим шляху завдання.)

**`reviews_left`** у `GET /portal/billing/outlook` — скільки перевірок поспіль пропустять двері
подачі: двері пускають, поки доступно ≥ P (ціна до здачі), а списують потім факт F, типово менший
за P. Формула — у docstring `outlook.py` (`reviews_left`). P і F — типові числа
[публічного знімка](#публічні-числа-public_numberspy) цього старту app (`review_cost.homework`):
P — `start_threshold.typical`; F — середнє списаного за останні 10 перевірок студента, без них —
`actual.typical`. Тож студент без власної історії, маючи юніти найменшого пакета, бачить те саме
число, що сайт (`smallest_package_reviews.typical`), і воно змінюється лише з перестворенням app.
Знімка немає (адреса відповіла б 503) — `null`. Група `homework` не `ready` (або в ній немає P) —
запасний шлях: P — ціна першого завдання курсу за типового розміру роботи (`_price_of_a_course_task`),
F — власне середнє студента, без нього — F = P; немає й цієї ціни — `null`.
`warning` — від того самого N: `next_may_fail` при N < 1, `low` при N < `billing_reminder_low_reviews`.

**`held_reviews`** у `GET /billing/outlook`: `{count, oldest_at, missing_units}` — перевірки студентів
цього орендаря, які автор оплачує за правилом і які чекають його юнітів; `missing_units` = сума P
утриманих мінус доступні, не менше 0 (з кредитом — 0); `count = 0`, коли таких немає.

**`GET /billing/spending`** — межі включно, дати UTC; за замовчуванням поточний місяць. Відповідь:
`{period: {from, to}, charging_enabled, totals: {billed_units, covered_units}, courses: [{course_node_id,
title, billed_units, covered_units, reviews_units, processing_units, preparation_units, tasks:
[{authored_document_id, title, reviews, billed_units, covered_units}]}], unlinked: {billed_units,
covered_units}}`.

* `billed_units` — рухи `debit` + `difference_arisen` на рахунку автора, прив'язані до дій;
  `covered_units` — `benefit_covered` + `platform_covered` (покрито пільгою чи платформою, не
  виставлено). Купівлі, повернення, згорання, резерви не входять. Числа додатні.
* `reviews_units`, `processing_units`, `preparation_units` ділять `billed_units` курсу за видом дії.
  У `tasks` — перевірки й підготовка завдання; обробка — курсу, не завдання.
* Перевірка студента, яку автор оплачує за правилом, — під своїм завданням.
* Дія без курсу (рядок зник) — у `unlinked`, не губиться.
* Жодних доларів (замок-тест). `from` після `to` — 422 `invalid_period`.
* Поки списання до рахунку автора не застосовне — нулі й `charging_enabled = false`.

## Публічні числа (`public_numbers.py`)

Рішення оператора 19–20.11: сайт, сторінка about, портал студента й панель автора показують ті самі
числа вартості перевірки й «на скільки вистачить» — з реальних даних бази, і джерело їх одне —
бекенд, адреса `GET /api/v1/public/numbers` (без входу й ключа).

**Що рахується** (`compute_public_numbers`, лише читання, по всіх орендарях):

* `packages` — активні пакети каталогу за зростанням юнітів, рядок на пару «пакет — валюта»:
  `id`, `units`, `price_minor`, `currency`, `validity_months` (`journal.VALIDITY_MONTHS`),
  `tax_mode` (каталог; `exclusive` — податок додається зверху, як налаштовано товар у посередника);
* `rules.reserve_multiplier` — `cost_estimate.core.RESERVE_MULTIPLIER` (резерв старту — 2E);
* `review_cost.homework` (`task`, `short_task`) і `review_cost.project` — вибірка: подачі останніх
  `PUBLIC_NUMBERS_WINDOW_DAYS` (типово 90) днів у стані `completed` / `delivered`. `actual` — факт
  кожної (`charging.review_facts_usd` одним запитом, `charging.fact_of`), нульові відкинуто: min,
  медіана (округлена, як факт при списанні, — половина вгору, `core.round_half_up`), max.
  `start_threshold` — P оцінки кожної перевірки з фактом, чинна `charging.price_of` її `e_usd` (не
  збережений `p_units`): медіана, округлена вгору (`core.round_up`: поріг не применшується), і max. `smallest_package_reviews` —
  `outlook.reviews_left` для юнітів найменшого пакета: `typical` — з типових P і F групи; `low` /
  `high` — найменше й найбільше з того самого числа по завданнях вибірки (медіани P і F завдання,
  округлені так само). Усі числа — цілі юніти, округлені один раз у знімку: сайт, портал і
  нагадування беруть саме їх і власного округлення не мають.
  `status`: `ready` — є перевірка з фактом; `insufficient_data` — немає (числа `null`);
  `not_charged` — тип зараз не списує юнітів (нинішній Ментор або тестовий режим шляху,
  `config/submission_paths.yaml`; проєкт сьогодні — нинішній Ментор). `sample.includes_internal` —
  завжди `true`: до набрання даних наші службові студенти у вибірці.
* Жодних id, імен, пошт чи даних окремої людини.

**Коли оновлюється — лише на старті app.** Знімок рахує lifespan (`api/app.py`) і кладе в Redis під
ключем цього старту контейнера (`start_key`: hostname — у Docker це id контейнера, новий на кожне
перестворення, — `boot_id` хоста й час старту процесу 1, батька uvicorn). Перший процес рахує й
пише `SET NX`, решта (і перезапущені uvicorn робітники) читають той самий ключ — **тому всі процеси
віддають ті самі байти, `as_of` і `ETag`**. Кожне читання продовжує життя ключа на 7 днів (`GETEX`):
ключі старих стартів зникають самі, ключ живого — ні. Між стартами знімок не змінюється, хоч би що
з'явилось у базі. Збій розрахунку старт не зупиняє: адреса відповідає 503 `numbers_unavailable` і
пробує знову на наступному запиті. Відповідь — `Cache-Control: public, max-age=300` і `ETag`;
`If-None-Match` з ним — 304. Окремого обмеження частоти немає: публічних адрес з лімітом за джерелом
у застосунку немає (вхід і посилання скидання обмежено за логіном), а відповідь — одне читання Redis.

Нагадування порталу (`reviews_left`) бере P і F з того самого знімка (вище).

## Звіт адміністратора про витрати

```bash
uv run python scripts/billing_admin.py costs [--from YYYY-MM-DD] [--to YYYY-MM-DD] [--tenant ...] \
    [--by author|student|both|task] [--format table|csv]
```

Транзакція READ ONLY. Поруч із собівартістю USD — юніти з журналу (`costs.BilledUnits`), виставлені
(`debit` + `difference_arisen`) двома стовпцями за рахунком, на якому рух:
`виставлено_авторові` / `billed_author_units` (рахунок автора) і `виставлено_студентам` /
`billed_students_units` (рахунки студентів орендаря); окремо `покрито_юнітів` / `covered_units`
(пільга чи платформа — не виставлено нікому). `платформа_usd` / `platform_usd` — частина собівартості
USD, яку не оплачує жоден платник (повтори, спроби, що впали на інфраструктурі, екран реплік —
`NOT charging.PAID_BY_PAYER`); у журнал вона не потрапляє.

* рядок автора — рухи на рахунках орендаря;
* рядок студента — рухи перевірок для цього студента, хто б не платив (автор за правилом — у
  стовпці автора);
* `--by task` — автор → курс → домашнє завдання через `links.link_actions`; обробка — рядок курсу
  «(без завдання)», дія без курсу — «(без курсу)».

У шапці таблиці — рядок `costs.DATING_NOTE`: долари датовано викликом, юніти — рухом журналу, тож
на межі періоду вони можуть розійтися (CSV лишається чистою таблицею, без цього рядка).
