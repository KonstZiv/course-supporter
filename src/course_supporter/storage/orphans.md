# Осиротілі об'єкти сховища (Б-2, прибирання архівів — частина друга)

Політика конфіденційності обіцяє: видалений матеріал курсу стирається зі сховища фоновим
завданням. До запиту №735 видалення розділу (`DELETE /nodes/{id}`) не віддавало в прибирання
архіви й знімки баз проєкту (`project_bases.archive_key`, `snapshot_key`). Нові видалення
прибираються; об'єкти розділів, видалених раніше, лишились у сховищі без жодного посилання з
бази. Ця команда знаходить їх і ставить у наявне прибирання **один раз**.

Код: `orphans.py` поруч; команда — `scripts/storage_admin.py`.

## Як запускати

На проді **спершу завжди `--dry-run`**. Справжній запуск — окреме рішення адміністратора.

```bash
docker exec -it course-supporter-app python -m scripts.storage_admin orphans \
    --actor <хто> --dry-run
```

Той самий рядок без `--dry-run` ставить сиріт у прибирання. `--min-age-hours` (типово 48)
ховає від команди об'єкти, молодші за вказане.

**`--dry-run`** нічого не пише й не ставить у чергу (до черги навіть не підключається).
Друкує кількості й сумарний розмір за категоріями (архів бази, знімок бази, інше) і кількість
орендарів. **Самих ключів не друкує**, і в журнал вони не потрапляють.

Приклад (числа з тесту `test_the_command_opens_no_queue_and_prints_no_key`):

```
storage orphans  dry run: nothing written, nothing queued
scanned 8 object(s), homework/ not listed; minimum age 0 h
not orphans: 0 referenced by a live row, 1 of a live node, 0 too young, 1 undetermined (the key names no node)
orphans (no live reference; the node of the key deleted or missing):
  archive        2 object(s)  3145728 B (3.0 MiB)
  snapshot       2 object(s)  1224288 B (1.2 MiB)
  other          2 object(s)  3245728 B (3.1 MiB)
  total          6 object(s)  7615744 B (7.3 MiB)
tenants: 2  (+ 1 object(s) with no tenant known)
```

Орендар відомий з ключа (`tenants/{t}/…`) або з рядка вузла; ключ старого вигляду
`{node_id}/…` вузла, якого вже немає в базі, орендаря не називає — такі рахуються окремо.

**Справжній запуск** не видаляє нічого сам. Він ставить ключі сиріт у `enqueue_s3_cleanup`
пачками по 500 (одне завдання `s3_cleanup` на пачку), а видаляє воркер `s3_cleanup_task` —
з повтором, як і для кожного видалення. Один структурований рядок журналу
`storage_orphans_enqueued` (у `--dry-run` — `storage_orphans_dry_run`) несе `actor`, `min_age_hours` і кількості (за категоріями, розмір,
орендарі, невизначені, завдання), без ключів. Повторний запуск після прибирання знаходить 0.

Код виходу: 0 — готово; 2 — помилка в аргументах; 3 — завдання створено, але ARQ його не
взяв (у виводі `NOT DISPATCHED`; запустіть команду ще раз — вона ідемпотентна).

## Що вважається сиротою

Об'єкт відра матеріалів — сирота, коли виконано **все** з трьох:

1. **(а)** на нього не посилається жоден **живий** рядок (таблиця нижче);
2. **(б)** вузол курсу, названий у ключі, м'яко видалений або не існує;
3. **(в)** він старший за `--min-age-hours` — щоб не зачепити завантаження, яке ще не
   дописало свій рядок.

Об'єкт, чий ключ не називає вузла (корінь відра, чужий вигляд ключа, «папка» без імені
файла), — **не сирота**: його лічильник «undetermined» у виводі, і команда його не чіпає.
Ключ називає вузол лише у виглядах, які пише застосунок:

| Вигляд ключа | Хто пише |
|---|---|
| `tenants/{t}/nodes/{n}/{uuid}/{ім'я}` | пряме завантаження за підписаним посиланням |
| `tenants/{t}/nodes/{n}/slides/{doc}/{NNNN}.webp` | відрендерені слайди презентації |
| `tenants/{t}/nodes/{n}/bases/{doc}/{uuid}/original.{ext}` | архів бази проєкту |
| `tenants/{t}/nodes/{n}/bases/{doc}/{uuid}/snapshot.zip` | знімок бази поруч з архівом |
| `{n}/{uuid}/{ім'я}` | завантаження через `upload_smart` (ровно три сегменти) |

### Які рядки посилаються на об'єкти

| Таблиця.поле | Що там | «Живий», коли |
|---|---|---|
| `authored_documents.source_url` | повний URL завантаженого файла (`{endpoint}/{bucket}/{key}`) або зовнішнє посилання; після м'якого видалення — мітка | `deleted_at IS NULL` |
| `authored_documents.slide_keys` | JSON-список ключів слайдів `.webp` | `deleted_at IS NULL` |
| `project_bases.archive_key` | ключ архіву бази | документ-власник `deleted_at IS NULL` |
| `project_bases.snapshot_key` | ключ знімка бази | документ-власник `deleted_at IS NULL` |
| `homework_submissions.file_url`, `.snapshot_key` | роботи студентів (`homework/…`) | команда їх не розглядає |

**`project_bases` не має `deleted_at`, і м'яке видалення не прибирає її рядків** — вони
лишаються після видалення документа (прибирає їх лише фізичне видалення через FK `CASCADE`).
Тому рядок бази вважається живим рівно тоді, коли живий його документ. Так само
`slide_keys` м'яко видаленого документа лишається в рядку, але посиланням не є. Без цього
архіви й знімки розділів, видалених до №735, захищав би власний осиротілий рядок.

`source_url` збігається за закінченням `/{ключ}`, тож збіг може бути ширшим, ніж треба (інший
ключ із тим самим закінченням) і ніколи не вужчим: помилка завжди на користь «лишити».

## Чому `homework/` не чіпається

Префікс `homework/` — роботи студентів і знімки їхніх проєктів. Це історія студента, а не
похідна розділу: видалення розділу її не торкається (зв'язок `homework_submissions` з
завданням `RESTRICT`), а прибирає й знеособлює її окремий процес — видалення облікового
запису студента (`student_deletion/README.md`). Ключ роботи не несе вузла, на який можна
спертись, тож «вузол видалений» для нього нічого не означає, а помилка тут стерла б чужу
роботу. Тому команда **не перелічує** цей префікс: відро обходиться за верхнім рівнем, і
`homework/` пропускається цілим — його ключів вона не бачить, не рахує й не ставить у
прибирання.

## Що B2 тримає після видалення

На проді відро — Backblaze B2. Видалення без вказаної версії лише **ховає** об'єкт: з
переліку він зникає одразу, а прихована версія лежить у відрі ще стільки, скільки задає
правило життєвого циклу самого відра (налаштування B2, не код застосунку). Тому
«стирається зі сховища» означає: зникає для застосунку негайно, з диска — після терміну цього
правила. Повторний запуск після прибирання знаходить 0: перелік (`ListObjectsV2`) показує лише
поточні видимі об'єкти.

## Межі

* Без міграцій; маршрути видалення не змінено (№735).
* Рядки `project_bases` видалених документів команда **не видаляє** — лишає, як і було.
* Рядки `jobs` (`input_params.file_keys` завдань `s3_cleanup`) зберігають ключі, як і для
  кожного видалення; воркер `s3_cleanup_task` логує `s3_delete` з ключем — це його
  наявна поведінка, команда її не змінює.
* Дві команди одночасно створять по завданню на ті самі ключі; видалення ідемпотентне
  (відсутній об'єкт — успіх), тож шкоди нема.
